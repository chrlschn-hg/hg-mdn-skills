# Building Frontend Applications Nuxt UI with Vite

## Overview

This application uses Vue and Nuxt UI <https://ui.nuxt.com/llms.txt> for components.  Configure with Vite (not Nuxt).

- Vue 3, Composition API, `<script setup lang="ts">`; TypeScript 6.x (not 7: `vue-tsc` does not support it yet); Tailwind CSS 4
- Pinia Colada (`useQuery`, `useMutation`) owns server state: caching, shared requests, cancellation; Pinia stores hold client state only; `src/queries` is the only code that calls the API; VueUse for reusable behavior
- File-based routing (`vue-router` 5): one `.vue` file in `src/pages` is one URL
- The API client **and Zod schemas** are generated by Kubb from the backend's OpenAPI document: never hand-written, never edited
- `oxlint` + `oxfmt` (Rust-based, fast; no ESLint or Prettier) for lint and format, set up at scaffolding (`references/project-structure.md`, "Toolchain"); Vitest + happy-dom + `@vue/test-utils` for tests; Playwright MCP to look at the running app
- Icons: `hugeicons` only, bundled at build (no runtime Iconify requests)
- One origin: the API is under `/api`; the runtime serves the built app in production (one container) and Vite proxies `/api` in development, so the client has no base URL and there is no CORS (`references/config-deploy.md`)
- The worked example in the references is a **Notes** feature: listings to copy when you first need a pattern, not code in a new project (`references/project-structure.md` says what the baseline ships)

The shape of a feature:

```text
backend endpoint --> generated client + zod schema --> queries/ --> page --> components
                                                         |           |
                                                  useQuery cache    AsyncContent (four states), UForm, USlideover,
                                                  useMutation       UTable, toasts, confirmations
                                                  SaveResult
```

## When to Use

Use when working on the front-end of the application.

- Vue components, pages, routing, layouts
- Queries, mutations, and stores; calling the backend API; handling its errors
- Forms, validation, dialogs, slideovers, tables, search, paging
- Frontend TypeScript development and testing
- Nuxt UI layout, theming, icons; accessibility and responsive behavior
- Front-end configuration, build, and deployment

## Instructions

<rules>
- Use the project's package manager; if none is set up, see the `hg-mdn-scaffold` skill.  Read the matching reference (index below) **before** writing code; starting a feature: `references/recipes.md`
- **Nuxt UI first:** components, slots, and props before custom markup or CSS; semantic color tokens (`text-muted`, `bg-elevated`); hugeicons as **literal** `i-hugeicons-*` names (`references/nuxt-ui.md`)
- **Routes are secure by default**, like the backend: signed-in unless `definePage({ meta: { public: true } })`; put `requiresAdmin` on a parent.  `returnUrl` is untrusted (`safeReturnUrl`).  Guards are UX; the backend enforces (`references/routing.md`)
- **Only `src/queries` calls the generated client** (and the session store through `queries/session.ts`); components call `useQuery(options)` and a mutation composable.  Direct `fetch`/`EventSource` only for what OpenAPI cannot describe, in one small module.  Read the function's JSDoc before calling it; never edit `src/api/generated` (a contract change comes from the backend: `mise run openapi`, commit the document, `npm run generate`, then let `vue-tsc` list the fallout)
- **Four states** for anything that loads, rendered by `AsyncContent` in this priority: error, loading, content, empty.  Skeletons only on the first load (`references/ui-states.md`)
- **Writes return a `SaveResult`** (`{ ok: true }` or `{ ok: false, code, message }`); switch on `code`, show `message`, never match message text (`references/api-client.md`)
- **Validate forms with the generated Zod schema** (`UForm :schema`); the backend stays the authority and its field errors show on the field (`references/forms.md`)
- **Server state is a query, never a store `ref`**: put every input in the query key, forward `signal`, invalidate after a write; do not hand-write loading flags, `latestLoad`, or shared promises.  Timers refresh with `refresh()`, never overlap, and stop with the component (`references/data-loading.md`).  Pinia stores hold client state only (`references/state-pinia.md`)
- **Confirm destructive actions; closing a form with unsaved text asks first; toast results** (`references/overlays.md`)
- **Components:** the page is the hub.  Pages and the app shell read queries and stores and pass state down as props; children report with typed events; `defineExpose` only for results that arrive after an emit.  Precompute row text in a `computed`; no calls or per-row lookups in a template (`references/components-composables.md`)
- **TypeScript:** strict; no `any`, `enum`, or `forEach` (use `unknown`, string unions, `for...of`); always brace; no Nuxt-only APIs (`useFetch`, `useState`, `@nuxt/*`).  `oxlint` enforces most.  File placement, style, comments: `references/project-structure.md`
- **Config:** only `VITE_*` variables reach the browser (public, baked in at build); never put a secret in one (`references/config-deploy.md`)
- **Tests:** use MSW for client and Colada integration; use `vi.mock` for focused boundaries and use a real Pinia with `PiniaColada` (never `createTestingPinia`); cover loading, error, empty, success, and a stale or failing response.  For any UI work get the **Playwright MCP** before you start, then look at the result: light and dark, narrow and wide, keyboard, console and network (`references/testing.md`)
- **Accessible by default:** every control has a name, real components rather than clickable `div`s, color never the only signal (`references/accessibility-responsive.md`)
</rules>

## Nuxt UI Templates

For complex layouts (dashboards, listing pages, inbox, settings, calendar, editor, chat), explore a matching template first; nothing needs to be copied.  Start with `dashboard`; use the Vue/Vite variants (`dashboard-vue`, `chat-vue`) where they exist.  Take the component composition; replace the data layer with queries and `i-lucide-*` icons with literal `i-hugeicons-*` names.  Key views, patterns, and what to adapt: `references/nuxt-ui-templates.md`.

## Commands

All scripts: `references/project-structure.md` ("Commands").  From the repo root: `mise run up` / `down`, `mise run test`, `mise run lint`, `mise run generate`, `mise run check`.

## Working Loop

1. Read the relevant reference(s) (`recipes.md` for a feature); open the nearest existing page, query, or component and copy its shape (one that ships, or the listing in the reference).  For a new complex screen, look at the matching Nuxt UI template view first.
2. If the backend contract is involved, review and commit the OpenAPI document before handlers exist (`mise run openapi`), regenerate (`npm run generate`), and let `vue-tsc` list what to update; read the new JSDoc.
3. Build against the generated stub mocks (`references/mocking.md`).  Write or change the query options and mutation composables (`src/queries`: key with every input, `signal`, `SaveResult` writes, invalidation), then the page and components that use them.
4. Add or update tests beside the code (query or mutation, component or composable, page); run `npm test`.
5. Look at it in the browser with the Playwright MCP (`aspire describe` gives the front-end URL): all four states, light and dark, narrow and wide, keyboard.
6. Hand off with the checklist in `references/recipes.md` (`mise run check`).
