# Project Structure and Tooling

A Vite SPA, **not Nuxt**: Nuxt UI is a plain Vue library through its Vite plugin.  The stack is in `SKILL.md`; this file owns where files go, naming, and the code conventions.

## Layout

```text
src/app/
  index.html
  vite.config.ts                  Nuxt UI plugin, router plugin, icon bundling, Vitest config
  kubb.config.ts                  OpenAPI -> TypeScript client
  tsconfig*.json  .oxlintrc.json  .oxfmtrc.json
  typed-router.d.ts               generated by the router plugin; committed
  auto-imports.d.ts  components.d.ts   generated; git-ignored
  src/
    main.ts                       creates the app: Pinia, router, Nuxt UI, API client setup
    App.vue                       <UApp> + <RouterView> (add a layout component when you need a shell)
    env.d.ts                      types for `VITE_*` variables
    assets/css/main.css           Tailwind + Nuxt UI imports
    pages/                        routes only: one file = one URL
    components/                   every other component, flat, feature-prefixed (auto-registered)
    layouts/                      app shell components and navigation data (created when needed)
    composables/                  `useX.ts` functions with their tests (created when needed)
    stores/                       Pinia stores (`x-store.ts`): the only code that calls the API
    router/                       guards (sign-in, admin, titles), `RouteMeta` types, `safeReturnUrl`
    utils/                        pure helpers (created when needed)
    api/
      <project>-api.json          OpenAPI document (backend build writes it; committed)
      errors.ts                   `toApiError`, `errorMessage`, `SaveResult`
      setup.ts                    `configureApiClient`: base URL override, credentials, 401 handling
      generated/                  Kubb output: clients, types, zod (git-ignored; never edit)
    test/                         `setup.ts` (network guard), `mount.ts`, `AppHarness.vue`
```

**Placement, one rule:** `pages/` holds routes only (every `.vue` file there becomes a URL).  Everything else is flat and feature-prefixed: `components/NoteForm.vue`, `composables/useClientList.ts`, `stores/notes-store.ts`, `utils/format.ts`.  There are no per-page folders: the prefix says which feature a file serves.

## Auto-imports

The Nuxt UI Vite plugin wires `unplugin-auto-import` and `unplugin-vue-components`; configure them through its `autoImport` and `components` options in `vite.config.ts`.

- **No import needed** for Vue APIs (`ref`, `computed`, `watch`, `onMounted`, ...), Pinia, `vue-router` (`useRoute`, `useRouter`, `definePage`), VueUse functions (`useStorage`, `useDark`, ...), and types like `MaybeRefOrGetter`.  Stores still import `defineStore` and `acceptHMRUpdate` from `pinia` explicitly (the HMR block reads clearer).
- **Not auto-imported:** VueUse constants such as `breakpointsTailwind`; import them.
- **Components:** every Nuxt UI component (`UButton`, `UCard`, ...) and every component in `src/components` is registered globally and typed in `components.d.ts`.  A component in `layouts/` or `pages/` is imported explicitly.
- Import explicitly: your own modules (`@/stores/...`), generated API code, types from libraries.
- If the editor does not recognize a new auto-import, run `npm run build` (or start `dev`) once to regenerate the `.d.ts` files.

## Aliases

`@/` is `src/` (in `vite.config.ts` `resolve.alias` and `tsconfig.app.json` `paths`).  Use it for anything outside the current folder; use relative imports within a folder.

## Conventions

- **Files:** components `PascalCase.vue`; composables `useThing.ts`; stores `thing-store.ts` exporting `useThingStore`; pages and folders `kebab-case`; dynamic segments `[id]`; tests beside the code (`thing.test.ts`).
- **SFC order:** `<script setup lang="ts">`, then `<template>`, then `<style scoped>` last, only when props, slots, and Tailwind cannot reach.
- **Props and emits:** type-only (`defineProps<{...}>()`, `defineEmits<{ confirm: [] }>()`), `withDefaults` for defaults; `defineModel` for two-way values; emit names in the type, camelCase in script and kebab in templates.
- **No calls or per-row lookups in a template.**  A single comparison, negation, or ternary prop is fine; anything more goes in a `computed` (`components-composables.md`, "View models").  Never write `.value` in a template.
- **Styling:** Nuxt UI props and slots first, then Tailwind utilities, then scoped CSS.  Use semantic color tokens (`text-muted`, `text-highlighted`, `bg-elevated`, `text-primary`) so dark mode works.  No CSS files beyond `main.css`.
- **Comments:** `/** ... */` on exported functions, store actions, and non-obvious props: a one-sentence summary, then the why; `@param name - ...` and `@returns` only where not obvious.  An HTML comment on a non-obvious template section (what it renders, why).  `// NOTE:` for traps.
- **TypeScript:** strict; `erasableSyntaxOnly` is on (no `enum`, no parameter properties; use string-literal unions or `as const` objects).  No `any`; use `unknown` and narrow.  `as` is a last resort: it silences the checker rather than proving anything.  Prefer `type` for object shapes and explicit types on exports.  No Nuxt-only APIs (`useFetch`, `useState`, `@nuxt/*`).
- **Always brace** `if`/`else`/`for`/`while` bodies, even one-liners.  Prefer `for (const x of xs)` to `xs.forEach(...)`: it supports `await`, `break`, and `return`.  `oxlint` enforces both and `no-explicit-any` (`curly`, `unicorn/no-array-for-each`, `typescript/no-explicit-any` in `.oxlintrc.json`).
- **Blank lines separate ideas:** keep single-line declarations of one concern together; add a blank line between a multi-line declaration and the next statement, between declarations and a call or condition, and before `return`.
- **Accessibility:** use Nuxt UI components (they wrap Reka UI primitives); label every input; icon-only buttons need `aria-label` (`accessibility-responsive.md`).

## Commands

Run in `src/app` (or `npm --prefix src/app run <script>`, or the `mise run` task):

| Command | Purpose |
|---|---|
| `npm run dev` | Vite dev server (Aspire runs this for you: `mise run up`). |
| `npm run build` | `kubb generate`, `vite build`, then `vue-tsc -b` (type-check). |
| `npm run generate` / `generate:watch` | Regenerate the API client from `src/api/<project>-api.json` (Aspire runs the watcher). |
| `npm test` | Vitest (`pretest` regenerates the client first). |
| `npx vitest run <file> -t "<name>"` | One file or test. |
| `npm run lint` / `lint:fix` | `oxlint` (TypeScript and Vue). |
| `npm run fmt` / `fmt:check` | `oxfmt`. |
| `npm run preview` | Serve the production build locally. |

From the repo root: `mise run up` / `down`, `mise run test`, `mise run lint`, `mise run generate`.  `oxlint` prints nothing and exits 0 when clean; `oxfmt` formats `.ts`, `.vue`, `.css`, `.json`, and `.md`.  Both read `.oxlintrc.json` / `.oxfmtrc.json` and skip `generated/`.

## TypeScript version

Stay on TypeScript 6.x.  `vue-tsc` needs the TypeScript JavaScript API (`typescript/lib/tsc`), which TypeScript 7's native package does not expose; `vue-tsc -b` fails with `ERR_PACKAGE_PATH_NOT_EXPORTED` on 7.  Revisit when `vue-tsc` supports 7.

## Configuration

Only `VITE_`-prefixed variables reach the browser, at build time.  `VITE_API_BASE_URL` (override the generated client's base URL; empty = same-origin) is declared in `env.d.ts`.  `VITE_BASE` (serve under a sub-path) is read by `vite.config.ts` from `process.env` when it loads, so it has no `env.d.ts` entry.  Details and the single-container deployment: `config-deploy.md`.

## Running it

`mise run up` starts everything; Aspire runs `npm install` (an installer resource), the Vite server (assigned port: `aspire describe`), and the Kubb watcher.  The generated client calls the backend directly; the template's CORS accepts any origin, so restrict it before you use cookie auth.  After a fresh clone, `npm run generate` (or `npm test`/`npm run build`) creates `src/api/generated`.

The official Nuxt UI skill and docs MCP are listed in `nuxt-ui.md`; the Playwright MCP is covered in `testing.md`.
